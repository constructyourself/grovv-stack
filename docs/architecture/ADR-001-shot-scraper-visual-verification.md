# ADR-001: shot-scraper for Agent Visual Verification

gro\\/\\/ stack — Architecture Decision Record

-----

## Status

Proposed — evaluation complete, awaiting approval before implementation.

-----

## Context

grovv stack mandates Playwright for E2E testing and gates it behind an ask-first rule: agents must never auto-generate E2E flows. That rule is correct, but it leaves a gap. During the testing and review phases an agent frequently needs to *see* a rendered page — to confirm a UI change landed, to check a component's layout, to verify an accessibility tree — without that need rising to the level of a committed E2E test.

Today the agent has no way to close that gap. The `code-review` agent's checklist contains `Accessible (WCAG 2.1 AA)` and `Responsive design`, both of which it currently "verifies" by reading JSX. It cannot look at the page.

[shot-scraper](https://github.com/simonw/shot-scraper) (Simon Willison, Apache-2.0) is a Python CLI over Playwright that captures screenshots, dumps accessibility trees, executes page JavaScript, and records console and network logs — all as one-line shell invocations with no test file, no config, and no repo artifacts.

-----

## Evaluation

### Verified Behavior

All findings below were confirmed by running shot-scraper 1.11 in a clean container.

| Check | Result |
|-------|--------|
| `pip install shot-scraper` | 9s; pulls Python Playwright 1.61, pydantic, click |
| Reuses an existing Playwright browser install | **No** — see Browser Duplication below |
| Single screenshot, cold start | 2.2s |
| Two screenshots via `multi` YAML | 1.4s total |
| `accessibility` output for a trivial page | 68 bytes — a formatted role/name list, not a raw AX blob |
| Agent can read the resulting PNG | Yes — the `Read` tool renders it into context |

### Browser Duplication

This is the significant cost, and it is not obvious from the documentation.

shot-scraper depends on **Python** Playwright, which maintains its own browser revision pin independent of a project's **Node** Playwright. A project that already has Playwright browsers installed does not satisfy shot-scraper. The observed failure:

```
BrowserType.launch: Executable doesn't exist at
/opt/pw-browsers/chromium_headless_shell-1228/chrome-headless-shell-linux64/chrome-headless-shell
```

The container had Chromium rev 1194 (Node Playwright); Python Playwright 1.61 demanded rev 1228, and the two use different internal directory layouts. `shot-scraper install` downloads a second Chromium — the existing one measured 597MB.

The practical consequence: **shot-scraper roughly doubles browser footprint in any project that already runs Playwright.** In CI that is a second cache to warm on every cold run.

### Overlap With Playwright

Playwright already provides `page.screenshot()` and `expect(page).toHaveScreenshot()`. The latter is a real visual-regression engine — baseline management, pixel diffing, diff artifacts on failure. **shot-scraper has no comparison capability whatsoever.** It captures; it does not compare.

For automated visual regression in a Playwright project, shot-scraper is strictly the worse tool. Adopting it for that purpose would be a mistake.

### Where shot-scraper Actually Wins

The value is in a different job — one Playwright is badly shaped for.

| Capability | Why it matters during testing and review |
|------------|------------------------------------------|
| Zero-artifact ad-hoc capture | The agent gets visual evidence without authoring a Playwright spec, a config, or a runner invocation — and without leaving files in the repo |
| `accessibility` tree dump | Makes the `code-review` checklist's WCAG item mechanically checkable. Compact and diffable — cheap to put in context |
| `--log-console` | Surfaces runtime console errors the diff alone cannot reveal |
| `--log-requests` (NDJSON) | Network waterfall for review of data-fetching changes, no instrumentation required |
| `-s` / `--selector` capture | Screenshot only the changed component, not the whole page — directly controls context cost |

The structural argument is the strongest one: grovv's ask-first Playwright rule exists to stop agents from generating E2E specs on their own initiative. shot-scraper satisfies the underlying need — the agent seeing the page — *without* tripping that rule. It complements the policy rather than eroding it.

-----

## Decision

Adopt shot-scraper, scoped narrowly.

**The boundary: shot-scraper produces evidence; Playwright makes assertions.**

shot-scraper output must never become a committed baseline. Doing so would build a visual-regression suite on a tool with no comparison engine, which is worse than having none.

### Component Shape

Ship it as a **baseline skill**, `visual-verification`, generated by skills-builder into the target project's `.claude/skills/` — not as a seventh baseline agent.

Rationale:

- grovv's six baseline agents are *roles* (frontend, backend, database). "Screenshot taker" is a capability, not a role. A seventh agent breaks that symmetry and forces edits to every doc that enumerates six.
- Skills are this repo's unit for procedures, and skills-builder customizes each one to the project's real stack — the actual dev-server command, the actual routes. An agent definition cannot do that.
- The `testing` and `code-review` agents get short pointer sections rather than duplicated procedure.
- The team-design step (harness, Step 7) may promote this to a dedicated agent for UI-heavy domains, where that is warranted. That is the correct place for the judgment call.

### Guardrails

These are load-bearing, not footnotes.

| Risk | Rule |
|------|------|
| Credentials at rest | `shot-scraper auth` writes session cookies to a plaintext JSON file. Must be gitignored, never committed, never pointed at production |
| Agent navigating arbitrary URLs | Default to localhost and the local dev server. Ask before any non-local URL |
| Arbitrary page JS | Never use `-j`/`--javascript` or `--bypass-csp` against a live authenticated app without explicit approval |
| CI cost and flakiness | Do not run shot-scraper in CI. Local and agent-session use only. This dodges both the second-browser cache cost and the screenshot-flakiness problem entirely |
| Context cost | Each screenshot read is a real image in context. Cap viewport dimensions; prefer selector-scoped captures of the changed component over full-page retina shots |
| Render non-determinism | Use `--reduced-motion`. Note that grovv's Alexandria font loads from fonts.bunny.net — a network failure silently changes rendering |
| Python in a TS/Go stack | Dev-tool only. Install via `pipx`/`uvx`, never as a project dependency, never in `package.json` |

### Ask-First Policy

Extend the existing rule rather than introducing a competing one:

- **No prompt** for captures against localhost or the local dev server — these are read-only and non-destructive.
- **Ask first** for any non-localhost URL, any use of stored auth, and any page JavaScript injection.
- The Playwright ask-first rule is unchanged. shot-scraper is not a route around it: needing an E2E test is still a conversation.

## Consequences

### Files Requiring Change

Per this repo's propagation rule, a capability addition must reach every doc that references the stack or the skill set:

| File | Change |
|------|--------|
| `docs/prompts/skills-builder.md` | Add `visual-verification` to the baseline skill table and the deliverable checklist |
| `grovv-stack-scaffold.md` | Step 5 skill table, Step 6 count (`~10` → `~11`), directory structure, stack reference table |
| `.claude/agents/testing.md` | Evidence-vs-assertions section; the boundary against Playwright |
| `.claude/agents/code-review.md` | Frontend checklist — visual evidence for UI diffs, a11y tree checked |
| `docs/prompts/team-design.md` | Harness cue: promote to a dedicated agent for UI-heavy domains |
| `CLAUDE.md`, `.claude/CLAUDE.md` | Testing standards and stack table |
| `README.md` | If it enumerates the skill set |
| `.claude-plugin/plugin.json` | Version bump 0.3.0 → 0.4.0 (behavior change installed users should receive) |

No change to the `agents` array — no new agent is added.

### Accepted Trade-offs

- A second Chromium (~600MB) in projects that already run Playwright. Mitigated by keeping shot-scraper out of CI, which confines the cost to developer and agent machines.
- A Python tool in a TypeScript/Go default stack. Accepted because it stays a dev tool and never enters the dependency graph.

### Rejected Alternatives

| Alternative | Why rejected |
|-------------|--------------|
| Seventh baseline agent | Capability, not a role; breaks the six-agent symmetry across every doc |
| shot-scraper for visual regression | No comparison engine. Playwright's `toHaveScreenshot()` is purpose-built and already mandated |
| Sections bolted onto the two agents, no skill | Procedure would be duplicated and could not be customized per project by skills-builder |
| Do not adopt | Leaves the review agent unable to verify its own accessibility and responsive-design checklist items |
